# ロボットのマイクで聞く

最終更新: 2026-08-24

## 決定

**音声入力は CoreS3 のマイク。** 2026-08-24、実機で通して確認し、
半二重による間が会話として問題ない水準だったため、この構成を本線にした。

それまでは「音声入力は PC のマイク」という設計だった。CoreS3 のマイクと
スピーカーが I2S を共有していて同時に開けないことが理由で、入力を PC に
逃がせばその制約を避けられる、という判断だった。制約自体は消えていないが、
**避けるほどの実害が無いと実測で分かった**ので、卓上ロボットとして自然な
「本体で聞く」構成を採った。

## 中心にある制約：マイクとスピーカーは同時に開けない

M5Unified の CoreS3 定義では、両方が同じ I2S を使う。

| | ポート | BCK | WS |
|---|---|---|---|
| スピーカー (AW88298) | I2S_NUM_1 | GPIO34 | GPIO33 |
| マイク (ES7210) | I2S_NUM_1 | GPIO34 | GPIO33 |

片方を開くには、もう片方を閉じるしかない（**半二重**）。
ロボットは喋っているあいだ耳が塞がる。

### そこから決まること

| | 結果 |
|---|---|
| 音響エコー | **構造的に起きない。** 鳴っている間マイクは物理的に閉じている |
| barge-in（喋っている最中に遮る） | **できない。** 聞いていないので割り込みを検知しようがない |
| 喋り終わってから聞けるまで | I2S の切り替え + ウォームアップ 120ms ぶんの間が空く |

**エコー対策と引き換えに barge-in を失った、というトレードオフ。**
元の構成（PC のマイク）なら barge-in は可能だが AEC が要る。こちらは
AEC が要らない代わりに、割り込みの手段を音声以外に求めることになる。

割り込みが欲しくなったら **タッチか IMU** を使う。どちらも既に PC へ
イベントが飛んでいるので、`audio_flush` を送れば黙らせられる。
頭を撫でたら黙る、のほうが卓上ロボットらしくもある。

## 使う

PC 側は既定でロボットのマイクを使う。特別な操作は要らない。

```powershell
.venv\Scripts\python -m pc.main
```

起動後、次の行が出れば耳から音が流れている。

```
CoreS3 のマイクから音が届きはじめました
```

### PC のマイクに切り替える

ロボットの聞こえが怪しいとき、原因がマイクなのかその先なのかを切り分ける。

```powershell
.venv\Scripts\python -m pc.main --pc-mic
```

恒久的に変えるなら `pc/config.yaml` の `audio.input` を `local` に。

### 実機なしで動かす

`tools/dummy_core.py --mic` が PC のマイクを CoreS3 のマイクとして中継する。
実機と同じく mic の開閉指示に従い、鳴っているあいだは自分で閉じる。

```powershell
.venv\Scripts\python -m pc.main
.venv\Scripts\python tools\dummy_core.py --mic --no-play
```

PC 側の経路そのものは `tools\core_mic_test.py` が自己テストしている（15項目）。

## 測る

```powershell
.venv\Scripts\python -m pc.main --check-mic
```

`audio.input` を見て、ロボットのマイクで録る。音量・SNR・VAD の切り出し・
モデル別の認識結果が出る。録音は `recordings/` に残るので、あとから
`--wav` で設定を変えて再解析できる。

**PC のマイクと比べること。** 同じ位置・同じ文で `--pc-mic` と比べると、
「ロボットのマイクだから」なのか「距離や音量の問題」なのかが分かれる。

> 対話ループが動いているとポート 8765 が塞がっていて `--check-mic` は
> 起動できない。止めてから実行する。

## 効きそうなつまみ

| つまみ | 場所 | 既定 | 効く場面 |
|---|---|---|---|
| `MIC_MAGNIFICATION` | `firmware/src/config.h` | 4 | 音が小さい。**まずここ**（M5Unified の CoreS3 既定は 2） |
| `audio.input_gain` | `pc/config.yaml` | 1.0 | 焼き直さずに試したいとき。素性は上のほうがよい |
| `MIC_WARMUP_MS` | `firmware/src/config.h` | 120 | 頭が切れる／開いた直後にノイズが乗る |
| `MIC_FRAME_SAMPLES` | `firmware/src/config.h` | 512 | 送信の粒度。16kHz で 32ms = PC 側 VAD の1フレーム |

## 仕組み

### プロトコル

| 向き | フレーム | 内容 |
|---|---|---|
| PC → CoreS3 | text | `{"t":"mic","on":true\|false,"rate":16000}` |
| CoreS3 → PC | binary | マイクの PCM（s16le mono / 512 サンプル = 32ms） |
| CoreS3 → PC | text | `hello` に `"mic":true`（マイクを持つ機体だという申告） |

16kHz × 16bit = 256kbps。Wi-Fi では問題にならない。

### PC 側

`RemoteMic`（`pc/audio/remote_mic.py`）が `Mic` と同じ形
（`sample_rate` / `frame_samples` / `queue` / `paused` / `start` / `stop` /
`frames`）を持つので、`UtteranceSegmenter` からは区別がつかない。
差し替わるのは `Rabbit.run()` の1箇所だけで、VAD より下は何も変わっていない。

`paused` に入れると **mic off をロボットに送る**。PC 側で捨てるだけでは
I2S をスピーカーに明け渡せないため。

### ファーム側

`mic_in`（`firmware/src/mic_in.cpp`）が半二重の切り替えを持つ。
**PC の指示より「いま鳴っているか」を優先する。** 指示の行き違いで
スピーカーとマイクが同時に開くと、どちらも壊れるため。

録音バッファを3枚で回しているのには理由がある。M5Unified は録音要求を
2枚まで先行して受ける。`record()` が戻った時点で「2つ前に投げた1枚」は
録り終わっているが、**2枚で回すとその1枚を次の `record()` が上書きする**。
3枚あれば、送っているあいだ次の録音を止めなくて済む。

## 測って分かったこと

### 弾いた区間（2026-08-24 / 73 件）

| | 値 |
|---|---|
| ピーク（中央値） | -21.3 dBFS |
| ノイズフロア（中央値） | -50.4 dBFS |
| SNR（中央値） | 17.1 dB |
| 区間の長さ（中央値） | 0.51s |

**レベルとしては悪くない。** 問題は長さのほうで、半分が 0.5 秒未満の
ゴミ区間だった。原因は VAD の長さ判定の不具合で、直してある
（[設計](dialogue-system.md)の「プリロールが長さの判定を殺していた」）。

なお 7 件はピークが 0 dBFS に張り付いていた。時刻から見て画面を叩いた音。

### 通した区間（2026-08-26 / 46 件）

`stt.save_heard: true` で貯めた、**本物の発話**のほうの統計。

| | 値 |
|---|---|
| ピーク（中央値） | -23 dBFS |
| SNR（中央値） | 22 dB |
| 振り切れ | **0 件** |

**`MIC_MAGNIFICATION` は触らなくてよい。** 8/24 に見えた振り切れは画面を
叩いた音で、発話には1件も無い。

SNR を変えて測った結果:

| 見たもの | 結果 |
|---|---|
| ウェイクワードの検出（本番と同じ経路） | **18/18**。SNR 22 / 15 / 10 dB のすべてで 6/6 |
| `medium` の誤り率 | SNR 11 dB でも 7.2%。しかも大半は表記ゆれ（多分／たぶん など） |

### 本当の原因は `_flush_input()` だった

「認識がうまくいかない」の原因は、音でもモデルでもなかった。

**文字起こしのあいだに届いた音を、毎回捨てていた。** 物音でも VAD は区間を
作るので、毎分 13 区間ほど拾ってはマイクを閉じ、推論に 700ms かけ、空の結果を
得て、そのあいだに届いた音を捨てる——を繰り返していた。時間の2割近く耳を
塞いだうえ、聞こえた分も捨てていたことになる。

直したのは2点（`pc/main.py`）。

- **喋る直前までマイクを閉じない。** 開閉は I2S の付け替えを伴い、開き直す
  たびにウォームアップ 120ms が乗る。物音由来の区間は何も喋らずに終わるので、
  そこで閉じると「聞こえない時間」を無駄に作る
- **喋ったときだけ入力を捨てる。** 掃除の目的は自分の声の残りを拾わないこと
  なので、何も喋っていないなら捨てる理由がない

あわせて `vad.threshold` を 0.5 → 0.6 に上げ、物音由来の区間そのものを減らした。

### 測って否定された仮説（もう試さなくてよい）

| 仮説 | 結果 |
|---|---|
| 区間を刻みすぎている | 0.45 秒の間で切っても誤り率は変わらない（6.4% vs 7.1%） |
| `temperature` を固定すれば安定する | 変化なし |
| faster-whisper の `vad_filter` を使う | 変化なし |
| マイクの増幅が過大 | 本物の発話に振り切れは1件も無い |

## 会話中だけ語彙プロンプトを渡す（2026-08-27 採用）

精度をさらに詰める手は2つ測ってあり、**副作用のないほうを採った。**

| 手 | 効果 | 代償 | 採否 |
|---|---|---|---|
| **会話中だけ**語彙プロンプト | 誤り率 7.2% → 3.3% | 実装十数行 | **採用** |
| `stt.beam_size` を 1 → 5 | 誤り率 7.2% → 5.8% | 遅延 +0.7 秒 | 見送り |

`beam_size` を見送ったのは、レイテンシが既に目標（1.6〜2.6s）を超えて 3.3s
あるため。**遅延を足さずに精度が上がるほうを先に採る。**

### なぜ「会話中だけ」なのか

語彙プロンプトを**常時**付けると、物音に文字が生えて「空」で終わる件数が
84 → 40 に減ってしまう。空が減るのは良いことではない——**物音が言葉になった**
という意味で、プロンプトの言葉を吐き戻して誤反応する。

会話ウィンドウの中なら、相手が話しかけていることが分かっている。そこにだけ
渡せば副作用が出ない。

```
呼ばれる前  stt.initial_prompt       （null のまま。物音しか来ない）
会話中      stt.conversation_prompt  （語彙を見せる）
```

出し分けは `Whisper.prompt_for()`（`pc/stt/whisper.py`）。会話中かどうかは
`WakeDetector.conversation_active` を `Rabbit.handle()` が渡す。

プロンプトは**長くしすぎないこと。** 長いほど吐き戻しが起きやすくなる。

`large-v3-turbo` は取得済み（`mobiuslabsgmbh/faster-whisper-large-v3-turbo`）
だが、medium がボトルネックではないので優先度は低い。
