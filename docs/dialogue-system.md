# ウサちゃんロボ 対話システム設計

最終更新: 2026-08-20

## 前提（確定事項）

| 項目 | 決定 |
|---|---|
| ハード | M5Stack CoreS3 |
| 可動 | なし（画面と音のみ）。可動は将来フェーズ |
| 構成 | PC母艦。重い処理は PC、CoreS3 は顔表示・音声出力・センサ |
| ゴール | 原作再現（池袋晶葉のウサちゃんロボ） |
| 音声入力 | **PC のマイク** |
| 音声出力 | **CoreS3 のスピーカー**（Wi-Fi 経由） |
| 起動 | ウェイクワード「ウサちゃん」 |
| LLM | **ローカル（Ollama）**。クラウド課金なし。Claude API へ差し替え可 |
| 役割分担 | 筐体・造形＝ユーザー / AI・ソフト＝Claude |

### 実行環境
- CPU: AMD Ryzen 7 7435HS (8C/16T) / RAM 16GB
- GPU: RTX 3050 Laptop **VRAM 4GB**
- Python 3.12.10, Node.js あり
- 導入済: Ollama / Python 依存パッケージ
- 未導入: VOICEVOX, PlatformIO

VRAM 4GB は **LLM が最優先で使う**。STT と TTS は CPU に回す。
LLM がレイテンシの支配項なので、ここに GPU を明け渡すのが正しい配分。

## 中核となる設計判断

### 1. レイテンシ：文単位ストリーミングパイプライン

対話ロボットの成否は応答内容より「間」で決まる。素朴な直列実装は壊滅する。

| 実装 | 初音出しまで |
|---|---|
| 直列（STT完了→LLM全文→TTS全文→再生） | 5〜8秒 |
| **文単位ストリーミング（設計目標）** | **1.6〜2.6秒** |

#### 実測値（2026-08-20 / VOICEVOX 導入後の通し計測）

| 区間 | 実測 | 備考 |
|---|---|---|
| VAD 終端検出 | 400ms | `hangover_ms` 設定値そのもの |
| STT（whisper medium / **GPU** / beam=1） | **413ms** | CPU の base で 976ms。GPU なら medium でも半分以下 |
| LLM 第1切れ | **0.9〜1.2s** | qwen3:4b-instruct |
| TTS 第1切れ（VOICEVOX / CPU） | **0.8〜1.1s** | 下記参照 |
| **初音出し（LLM+TTS のみ、`--text` 実測）** | **2.25s** | |
| **全体（VAD+STT+LLM+TTS の積算）** | **約 2.8s** | 目標 1.6〜2.6s をわずかに超過 |
| モデル初回ロード | LLM 6.5s / whisper 1.3s / VOICEVOX 話者 3.4s | 起動時に済ませる |

#### TTS が支配項だった

VOICEVOX の CPU 合成は **RTF 約 0.5**（1秒の音声を作るのに0.5秒）。
固定オーバーヘッドが約400ms あり、そこに文字数比例分が乗る。

| 文字数 | 合成時間 |
|---|---|
| 8 | 771ms |
| 10〜11 | 998〜1108ms |
| 18〜19 | 1319〜1399ms |

**RTF < 1 なので、2文目以降は前の文の再生中に合成が終わる。**
つまり初音出しを決めるのは第1切れの長さだけ。ここから2つの対策を入れた:

1. **第1切れだけ早く切る**（`FIRST_CHUNK_CHARS = 12`）
   最初の読点で切って先に喋りはじめる。2文目以降は通常どおり40字。
   これで初音出しが **2.5〜3.0s → 2.0〜2.3s** に縮んだ。
2. **起動時に `initialize_speaker` を叩く**
   未初期化の話者は初回合成が数秒遅れる。起動時に3.4秒払って解消しておく。

### 2. ウェイクワード：VAD + whisper による判定

専用のウェイクワードモデル（openWakeWord / Porcupine）は使わない。

1. Silero VAD が発話区間を切り出す（無音時は何も走らない）
2. faster-whisper で文字起こし
3. 「うさちゃん」を部分一致で判定（ひらがな正規化で表記ゆれを吸収）

追加のモデル学習が不要で、日本語がそのまま動き、
ウェイクワードの変更が設定1行で済む。

**一発発話に対応する**: 「ウサちゃん、今日の天気は？」のように1発話に
ウェイクワードと用件が両方入る場合、ウェイクワードを除いた残りが空でなければ
それを即クエリとして扱う。空なら「呼ばれた」反応を返して会話ウィンドウを開く。

**会話モード**: 一度起動したら20秒はウェイクワード不要。
毎回名前を呼ばせるのは相棒感を殺す。

#### 実装してみて分かった落とし穴

**whisper は「ウサちゃん」を「おさちゃん」と綴る。**
初期実装では取りこぼしが 3/5 発生した。名前を呼んでも反応しないロボットは
壊れているのと同じなので、対策を検証した。

最初は `initial_prompt`（固有名詞を先に見せて綴りを安定させる）が効くと考えたが、
**実測すると逆効果だった。** 似た音まで引き寄せて誤反応を生む。

| 構成 | 取りこぼし | 誤反応 |
|---|---|---|
| initial_prompt あり / fuzzy=1 | 0/5 | **1/10**（「お茶ちゃんと飲んでる？」→「ウサちゃんと飲んでる?」） |
| initial_prompt あり / fuzzy=0 | 0/5 | 1/10 |
| **initial_prompt なし / fuzzy=1** | **0/5** | **0/10** |
| initial_prompt なし / fuzzy=0 | 3/5 | 0/10 |

**採用: `initial_prompt: null` + 編集距離1のあいまい一致。**
あいまい一致だけで取りこぼしも誤反応もゼロになる。

用件の認識品質は両者でほぼ同等だった（差はウェイクワードの綴りだけで、
そこはあいまい一致が吸収する）。`initial_prompt` を足す理由がない。

#### whisper の幻聴を捨てる

「言っていないのに『ご視聴ありがとうございました』と認識される」という
報告を受けた。whisper が字幕を大量に学習した副作用で、**無音やノイズだけの
区間を渡すとこの文を返す**という既知の挙動。

再現させて計測したところ、判別は容易だった。

| 入力 | no_speech_prob | 出力 |
|---|---|---|
| 本物の音声 | **0.05〜0.08** | 正しい認識結果 |
| ノイズのみ | **0.91〜0.96** | 「ご視聴ありがとうございました」 |

**モデル自身は「これは音声ではない」と 9 割超の確度で判定している。**
その信号を捨てていたのが原因だった。

faster-whisper には `no_speech_threshold` があるが、**`avg_logprob` との
AND 判定**なので効かない。今回の幻聴は logprob が -0.57 と正常値のため、
組み込みフィルタを通り抜ける。`no_speech_prob` 単独で判定するようにした。

しきい値は 0.6。本物 0.08 以下・幻聴 0.91 以上で 0.83 も間が空いており、
本物を巻き込む余地はない。

**ただし確度だけでは足りなかった。** 「最後までご視聴ありがとうございました」
「以上、チャンネルをご覧いただきありがとうございます」といった長い変種の報告を受けたが、
合成ノイズでは再現できなかった。かすかな実音声など、モデルが自信を持つ条件で
出ていると考えられ、その場合 no_speech_prob では止まらない。

そこで**既知の文言による2層目**を足した。設定に部分一致のパターンを持たせ、
新しい変種を見つけたら足せるようにしてある。

  1層目: no_speech_prob > 0.6 で捨てる（原理的・確実）
  2層目: 既知の文言に部分一致で捨てる（すり抜け対策・要メンテ）

2層目は「ロボットに話しかける言葉として出る可能性が低いもの」だけを入れる。
「ありがとう」のような一般語を入れると本物の発話まで消える。
実際に「今日も一日ありがとうございました」が通ることを確認している。

なお **VAD は白色ノイズを完全に弾いていた**（10 秒流して 0 区間）。
実環境で幻聴が出るのは、テレビや物音のような**音声に似た音**が VAD を
通るため。VAD を締めるより、STT 側で確度を見て捨てるほうが筋がよい。

#### STT のモデルとデバイス

| | 平均 | ウェイクワード | 用件の認識 |
|---|---|---|---|
| tiny / CPU | 512ms | 7/7 | 「いい**点気**だね」「お腹**水**だ」と崩れる |
| base / CPU | 976ms | 7/7 | 正確 |
| **base / GPU** | **114ms** | **7/7** | **正確** |

**GPU が圧勝。** VRAM は +209 MiB しか使わず、LLM と同居させても
Ollama の GPU/CPU 配分は 27%/73% のまま変わらなかった。

Windows では cuBLAS / cuDNN が PATH 上にないと、モデルのロードは通るのに
最初の推論で落ちる。`_ensure_cuda_dlls()` が起動時に自動で PATH を通し、
それでも失敗したら CPU にフォールバックする。

#### 実マイクは合成音声よりずっと難しい

ここまでの検証は VOICEVOX のクリーンな合成音声で行っていた。
実マイクで試したところ、**呼びかけには反応するが用件を正確に聞き取れない**
という報告を受けた。合成音声で誤反応0だったからといって実音声で大丈夫にはならない。

切り分けのため `--check-mic` / `--wav` 診断を実装した。
録音レベル・SNR・VAD の切り出し本数・モデル別の認識結果を一度に出す。
録音は `recordings/`（gitignore 済み）に残り、`--wav` で何度でも再解析できる。

##### 実測（ユーザーの実マイク・2回）

| | 実行1 | 実行2 |
|---|---|---|
| ピーク | -11.6 dBFS | -18.8 dBFS |
| SNR | 25.7 dB | 19.2 dB |
| VAD | 1本を正しく検出 | 1本を正しく検出 |

**マイクも VAD も問題なし。原因はモデルの力不足だけだった。**
測る前に「マイクが悪いのでは」と当たりをつけていたら外していた。

同じ発話「ウサちゃん、今日はいい天気だね」に対する認識:

| モデル | 実行1 | 実行2 | 時間 |
|---|---|---|---|
| base | さて、今日は**イーテンキ**だね | さちゃん今日はいい**てんきらね** | 100ms |
| small | **うさちゃん**今日は良い天気だね | うさちゃん今日は良い天気だね | 209ms |
| **medium** | **ウサちゃん、今日は良い天気だね** | ウサちゃん、今日は良い天気だね | 463ms |

**medium を採用。** `beam=5` にしても結果が変わらなかったので `beam=1` でよい
（大きいモデルではビームサーチが効かない）。

##### VRAM は足りた

4GB では medium は載らないと踏んでいたが、実測すると収まった。

| 構成 | VRAM | Ollama の GPU/CPU 配分 |
|---|---|---|
| LLM のみ | 2940 MiB | 27%/73% |
| + small | 3372 MiB (+432) | 27%/73%（不変） |
| **+ medium** | **3616 / 4096 MiB (+596)** | **27%/73%（不変）** |

LLM の第1切れも 1049ms で劣化していない。**推測せず測ること。**

当初は「tiny で判定 → ヒットしたら base で再認識」の2段構成を検討したが、
呼びかけられた発話では両方走って合計1.5秒になり base 単体より遅い。
2段構成が有利なのは CPU 使用率であってレイテンシではないので、単段にした。

### 3. 待ち時間は演出で埋める

1.6 秒はまだ「間」が空く。技術で消せない分は CoreS3 の顔で埋める。

状態機械 `idle / listening / thinking / speaking` を PC 側で持ち、遷移のたびに CoreS3 へ push する。**耳がぴくっと動く・目が上を向いて考える**——この 0.5 秒が入るだけで、待ち時間が「無視」から「反応」に変わる。可動を捨てた構成だからこそ画面の演出が効く。

### 4. barge-in と音響エコー

喋っている最中に話しかけられたら即座に黙る。生き物っぽさが段違いに変わる。

実装自体は単純（PC 側 VAD が発話を検出 → TTS キュー破棄 + CoreS3 へ `audio_flush`）。
**難しいのは音響エコーのほう。**

マイクとスピーカーが同じ空間にある以上、ウサギの声を自分のマイクが拾う。
素朴に barge-in を有効にすると、**自分の声に自分で割り込んで即座に黙る**。

| 構成 | エコー経路 | 対策 |
|---|---|---|
| Step 1（PC マイク + PC スピーカー） | 至近距離。最悪 | 再生中はマイクを閉じる（barge-in 無効） |
| 最終形（PC マイク + CoreS3 スピーカー） | 部屋を挟むが依然あり | AEC が要る |

**Step 1 では `behavior.barge_in: false` とし、再生中はマイクを閉じている。**
再生終了後にマイクの滞留フレームを捨てて VAD をリセットしてから待受に戻る
（これをやらないと、自分の声の残りを次の発話として拾う）。

有効化は Step 5。AEC を入れるか、「現在読み上げ中のテキストと一致する認識結果は無視する」
という簡易フィルタで妥協するかは、そのとき実測して決める。

**CoreS3 のバッファ長は barge-in の応答性と Wi-Fi ジッタ耐性のトレードオフ。300ms を初期値とする。**
長くすると途切れにくいが、割り込んでから黙るまでが鈍くなる。

> barge-in は「喋りながら聞く」＝全二重を要求する。CoreS3 の内蔵マイクとスピーカーは
> I2S を共有していて同時使用に制約があるため、**入力を PC 側に置いた本構成は
> この問題を構造的に回避している。**

### 5. 感情表現：インラインタグ

LLM に `[喜]` `[困]` `[驚]` のようなタグを本文中に吐かせ、TTS に渡す前に剥がして表情 state に変換する。

JSON 構造化出力は使わない——ストリーミングが崩れて文単位パイプラインが死ぬ。

### 6. LLM はローカルで動かす（Ollama）

クラウド API を使わないので**課金はゼロ**、レート制限もなく、ネット接続も不要。
PC さえ動いていればウサギは喋る。

`llm/client.py` は Ollama と Claude API を同じインターフェースで扱う。
`config.yaml` の `llm.backend` を `claude` にすれば差し替わる（要 `ANTHROPIC_API_KEY`）。
その場合はペルソナを system に置いて prompt caching を効かせ、`effort: low` で使う。

#### モデル選定で判明したこと（重要）

**推論（thinking）モデルは対話ロボットに使えない。**

最初 `qwen3:4b` で試したところ、以下の挙動になった:

| 設定 | 結果 |
|---|---|
| `think` 指定なし | 思考が `message.thinking` に分離される。ただし本文が出るまで10秒以上かかる |
| `think: false` | 思考が止まらず、**生の推論が英語のまま `content` に流れ込む** |
| `/no_think` soft switch | 効かない |

`think: false` は「Ollama が思考を分離しなくなる」だけで、モデルの思考自体は止まらない。
対話ロボットでは**非推論モデルを選ぶこと**。

#### 採用: `qwen3:4b-instruct`

非推論版に変えたところ、思考ゼロ・初トークン 0.68s で期待どおり動いた。
日本語も自然で、ペルソナの口調（一人称・語尾）も守れる。

**VRAM には収まりきらない。** 4GB に対して `num_ctx=4096` で 33%、
`num_ctx=2048` で 27% が CPU にこぼれる。実測では 2048 のほうが速いのでそちらを採用。

#### 3B 級との比較（VRAM に載る vs 品質）

| | qwen3:4b-instruct | qwen2.5:3b |
|---|---|---|
| VRAM | 3.2GB / **27% が CPU** | 2.1GB / **100% GPU** |
| 第1文まで | 0.81s | **0.51s** |
| 一人称 | ボク（正しい） | 「私」になる |
| 語尾の活用 | 正しい | 「だのだ」等の誤りが再発 |
| その他 | — | **ペルソナ内の Markdown 記号をそのまま読み上げ文に混ぜる** |

速度では 3B が勝つが、**品質差が大きいので 4B-instruct を採用**。
0.81s は目標に対して十分に余裕がある。

なお 3B が Markdown を混ぜてきた件を受けて、
ペルソナから強調記号を排除し、TTS 直前に `sanitize_for_tts()` を通す対策を入れた。
モデルを変えても読み上げが壊れないようにするための保険。

#### ペルソナ側の注意

4B 級モデルは語尾の活用を間違える（「ロボットだのだ」など）。
`persona/usachan.md` に**文法規則を明示**したところ解消した。
小型モデルでは「正しい例と誤った例をセットで書く」のが効く。

### 7. ペルソナは3層に分ける

public リポジトリなので、原作由来の情報とそうでないものを分離する。
起動時に上から順に連結して system prompt にする。

| # | ファイル | 公開 | 内容 |
|---|---|---|---|
| 1 | `persona/usachan.md` | される | 誰であるか。自作の説明文のみ |
| 2 | `persona/usachan.local.md` | されない | 口調・セリフ例（原作由来） |
| 3 | `persona/rules.md` | される | 出力フォーマットの規則 |

**規則（3）を最後に置くのが要点。** 小型モデルは前半の指示を忘れやすく、
セリフ例の後ろに置くほうが守られる。

#### 実装してみて分かったこと

**その1: コメントの中に書いた内容は消える。**

テンプレートの説明文を `<!-- -->` に入れていたところ、その隣にセリフを
貼るのが自然な導線になっており、683文字が丸ごと捨てられて46文字しか
プロンプトに渡っていなかった。テンプレート設計の失敗。

対策として、雛形の記入欄をコメントの外に出したうえ、
読み込み時に「中身の大半がコメント内」を検知して警告するようにした。

**その2: 仮のペルソナは口調まで作り込まないほうがよい。**

セリフ例が手に入るまでの仮ペルソナに「一人称はボク」「語尾は〜なのだ」と
書いていたが、実際の口調はまったく違った。仮の作り込みが本物と衝突し、
「違和感がある」という評価につながった。

原作を把握していない部分は埋めず、局所ファイル側に委ねる構造にした。

**その3: 履歴からタグを剥がすと、モデルがタグを付けなくなる。**

返事の先頭に `[喜]` などの感情タグを付けさせているが、付与率が 2/10 しか
なかった。原因は、TTS に渡す前にタグを剥がした文を**そのまま会話履歴に
保存していた**こと。モデルは自分の過去の発言を見て「自分は普段タグを
付けない」と学習し、数ターンで止めてしまう。

履歴にはタグを復元して保存するようにしたところ、**付与率が 10/10 になった。**
出力を後処理してから履歴に積む設計は、この種の自己強化を起こしやすい。

## PC ⇄ CoreS3 プロトコル

WebSocket。**CoreS3 がクライアント**として `ws://<pc-ip>:8765/rabbit` に接続する（PC 側の IP 固定だけで済み、CoreS3 側の IP を知る必要がない）。

### PC → CoreS3

| フレーム | 内容 |
|---|---|
| text | `{"t":"state","v":"idle\|listening\|thinking\|speaking","emotion":"neutral\|happy\|puzzled\|surprised\|sleepy"}` |
| text | `{"t":"audio_begin","rate":24000,"ch":1,"fmt":"s16le"}` |
| binary | PCM チャンク（20ms = 960 bytes @ 24kHz mono s16） |
| text | `{"t":"audio_end"}` |
| text | `{"t":"audio_flush"}` — barge-in。バッファ即破棄 |

### CoreS3 → PC

| フレーム | 内容 |
|---|---|
| text | `{"t":"hello","fw":"0.1.0"}` |
| text | `{"t":"touch","x":..,"y":..}` |
| text | `{"t":"imu","event":"lift\|shake\|pat"}` |

### 補足
- VOICEVOX の出力は 24kHz / 16bit / mono。そのまま流して 384kbps——Wi-Fi では問題にならない
- プリバッファ 100ms 溜まってから再生開始（ジッタ吸収）
- **口パクは CoreS3 側で PCM の RMS から計算する。** PC 側で計算して送るより、再生バッファそのものを見るほうが同期が正確

#### レイテンシの現在地

| 区間 | 実測 |
|---|---|
| VAD 終端検出 | 400ms |
| STT（medium / GPU / beam=1） | 413ms |
| LLM 第1切れ | 1190ms |
| TTS 第1切れ | 1250ms |

**残る支配項は LLM 1.2s と TTS 1.0s で、どちらもこのハードの素の速度。**
これ以上詰めるならモデルを小さくするしかないが、品質を落とすと本末転倒。

## 公開リポジトリとしての制約

このリポジトリは public（https://github.com/minato80000/AI-Rabbit）。
**原作の文章は一切コミットしない構成にしている。**

### ペルソナの2層構造

| ファイル | 公開 | 内容 |
|---|---|---|
| `pc/persona/usachan.md` | される | 人格・話し方・応答ルール。自作の説明文のみ |
| `pc/persona/usachan.local.md` | されない | 原作のセリフ例など著作物にあたるもの |
| `pc/persona/usachan.local.md.example` | される | 上を作るためのテンプレート（中身は空） |

`load_persona()` がベースを読み、ローカル側が存在すれば追記する。
存在しなければベースだけで動くので、クローンした人もそのまま起動できる。

### 二重の保護

1. **`.gitignore`** — `*.local.md` をどの階層でも除外
2. **pre-commit フック**（`tools/hooks/pre-commit`）— `git add -f` で
   強制ステージしてもコミットを中止する

フックはリポジトリに入れてあり、`git config core.hooksPath tools/hooks` で有効化する
（`.git/hooks` はクローンで配布されないため、この方式にしている）。
`*.local.yaml` と `.env` も同じフックで弾く。

### 検証済み

- 通常の `git add -A` では `usachan.local.md` はステージされない
- `git add -f` した状態で `git commit` すると中止される
- ローカルファイルの有無で `load_persona()` が正しく切り替わる
